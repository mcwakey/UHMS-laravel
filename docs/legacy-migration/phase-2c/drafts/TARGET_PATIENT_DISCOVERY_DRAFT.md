## 1. Confirmed installed `patients` contract

The installed table has 46 columns, InnoDB, `utf8mb4_unicode_ci`, and no database trigger. The installed database contains no views, triggers, scheduled events, or stored routines. Application runtime is therefore the principal side-effect source.

### 1.1 Mandatory identity columns

| Column | Installed database contract | Operational/application contract |
|---|---|---|
| `id` | unsigned bigint auto-increment primary key | Target-generated. Classic keys must never be reused. |
| `patient_number` | `varchar(191)`, non-null, unique | Generated by `PatientIdGeneratorService`; Classic OPD is never supplied here. Uniqueness includes soft-deleted rows. |
| `first_name` | `varchar(191)`, non-null | Store/update request: required string, maximum 100. No automatic normalization in service/model. |
| `last_name` | `varchar(191)`, non-null | Store/update request: required string, maximum 100. No automatic normalization in service/model. |
| `date_of_birth` | `date`, non-null | Store/update request: required date strictly before today. `Patient` casts to date. No database range/check constraint. |
| `gender` | `varchar(191)`, non-null | `Gender` cast and request enum allow exactly `male`, `female`. No database check; unsupported stored strings can fail on hydration. |
| `phone` | `varchar(191)`, non-null, indexed but not unique | Store/update request: required, max 20, country-configured regex. Current Ghana setup accepts exactly `^(?:\+233|0)[235][0-9]{8}$`. No normalization is performed before storage. |

Policy consequence confirmed by D-213/Q-007: missing or invalid first name, last name, DOB, gender, or phone cannot be filled with placeholders. The patient and dependent source chain must remain quarantined until evidenced remediation or an approved target representation exists.

The form maximum of 100 for each name component is stronger than the installed `varchar(191)`. A migration-specific contract must treat values over 100 as operationally unrepresentable unless a controlled exception explicitly approves a different target rule; it must not silently use the larger physical capacity or truncate. The same physical/logical distinction applies to phone (`191` versus form maximum `20`).

The installed `patients.emergency_contact_name`, `emergency_contact_phone`, and `emergency_contact_relationship` columns remain nullable physical columns, but they are absent from `Patient::$fillable`, store/update patient rules, and current patient displays. Current code writes and reads `emergency_contacts` child rows. These legacy inline columns are not the approved contact destination and should remain unused; child contact mapping is Phase 2D.

### 1.3 Status, merge, death, and timestamp columns

- `status`: non-null string default `active`; code uses `active`, `inactive`, `archived`, and `deceased`, but neither DB nor enum enforces the set.
- `is_active`: non-null boolean default true. Application code expects it to agree with status, but there is no check constraint.
- `is_temporary`: non-null boolean default false; `temporary_reason`, `identity_confirmed_at`, and `identity_confirmed_by` are nullable. Operational emergency services deliberately create placeholder temporary identities; that behavior is prohibited for migration.
- `merge_status`: non-null `varchar(20)` default `ACTIVE`; merged folders use `MERGED`. `merged_to_patient_id`, `merged_at`, and `merged_by` are nullable. The database does not enforce acyclic merge chains, status coherence, or terminal-folder eligibility.
- `is_deceased`: non-null boolean default false; death date/details/actor are nullable. `PatientService::markDeceased()` stamps the current actor and changes status at runtime.
- `registered_by`: nullable user FK, detailed separately below.
- `created_at`, `updated_at`, `deleted_at`: nullable timestamps. `Patient` uses Eloquent timestamps and soft deletes, so ordinary `create()` invents current timestamps. Historical persistence must explicitly preserve valid source timestamps and use null/provenance when no source registration time exists; it must not allow Eloquent to stamp migration time.

No database constraint keeps `status`, `is_active`, `is_temporary`, `merge_status`, `merged_to_patient_id`, death fields, or identity-confirmation fields mutually consistent. Those combinations are service/application invariants and require explicit validation.

## 3. Patient numbering and sequence contract

### 3.1 Confirmed runtime configuration

The installed local runtime currently resolves:

- prefix: `UHMS`;
- pattern: `{PREFIX}-{SEQUENCE}/{YEAR}`;
- sequence width: 6;
- reset period: yearly;
- application timezone: UTC.

This differs from the repository fallback pattern `{PREFIX}-{YEAR}-{SEQUENCE}`. Runtime configuration, not the fallback example, determines committed target numbers. Configuration fingerprinting is therefore a Phase 3 prerequisite.

Installed `patient_number_sequences` contract:

- `prefix varchar(20)` non-null;
- native enum `period_type` in `never`, `yearly`, `monthly`, `daily`;
- `period_key varchar(20)` non-null;
- unsigned `last_sequence` default 0;
- unique `(prefix, period_type, period_key)` named `pns_unique`.

### 3.2 Confirmed service behavior and defects for migration use

`PatientIdGeneratorService::generate()`:

1. resolves the current period from `now()`;
2. starts a database transaction;
3. locks an existing sequence row with `lockForUpdate()`;
4. inserts a missing row and reacquires it;
5. increments `last_sequence` and commits;
6. formats the number from current time/configuration;
7. checks `patients.patient_number` for a collision;
8. on collision appends a four-character value derived from `uniqid()` rather than failing.

The lock is a valid concurrency invariant for an existing period row, but the unchanged service is not migration-safe:

- it has no source crosswalk lookup and is not idempotent;
- dry-run would mutate sequence state;
- normal `PatientService::create()` allocates/commits a sequence before inserting the patient and has no encompassing transaction, so a failed insert consumes a number;
- the collision suffix is nondeterministic, is not sequence-reconcilable, and is not rechecked for uniqueness;
- first allocation in a new period can race on the unique sequence-row insert and has no retry;
- current time determines the period/year, not the historical registration date;
- rollover during a long migration changes the number period unless controlled;
- it does not persist the protected source mapping atomically.

`Patient::generatePatientNumber()` is a separate old helper using `PT-YYYYMMDD-NNNN`, maximum-by-string lookup, and no lock. It is not the renewed numbering authority and must never be used by migration.

### 3.3 Required future allocation boundary

The future migration persistence boundary must preserve the configured prefix/pattern/period/width and locked monotonically increasing sequence invariant, but must not call `PatientService::create()` unchanged. It must:

- look up the protected source-to-target patient mapping before any allocation;
- perform mapping reservation, sequence increment, patient insert, and successful crosswalk completion in one controlled transaction or an equivalently reviewed recoverable protocol;
- lock the exact configured sequence row and safely create/retry a missing period row;
- check all target patients, including soft-deleted rows, for collision;
- stop on a collision instead of adding a suffix;
- never allocate during dry-run; dry-run may report a symbolic `TARGET_GENERATED_AT_COMMIT` outcome and capacity/preflight state only;
- on retry/resume, return the mapped target patient and existing number without sequence mutation;
- on transaction rollback, leave neither a successful mapping nor a replacement number; any intentionally consumed gap must be recorded and reconciled;
- fingerprint runtime numbering configuration and stop if it changes between preflight and commit;
- serialize with concurrent operational registration through the same sequence row lock, or require a controlled registration freeze;
- explicitly handle UTC period rollover as a stop/restart boundary;
- reconcile `last_sequence`, committed target numbers, mapping cardinality, duplicate count, rollback gaps, and soft-deleted number reservations.

Policy assertions: Classic PK reused as target ID = 0; Classic PK reused as patient number = 0; Classic OPD used as patient number = 0; successful source patient with more than one target number = 0; successful rerun generating a replacement number = 0; nondeterministic collision suffixes generated by migration = 0.

## 4. Alias target contract and gap

Installed `patient_aliases`:

- required target `patient_id` FK, cascade on force delete;
- nullable `source_patient_id` FK to another **target patient**, set null on force delete;
- required `alias_type varchar(50)`, `alias_value varchar(191)`, `normalized_alias_value varchar(120)`;
- nullable longtext `metadata` cast to array and nullable `created_by` FK;
- unique `(alias_type, normalized_alias_value)` under `utf8mb4_unicode_ci`;
- no soft deletes and no model activity logging.

`source_patient_id` is for the target duplicate-folder merge workflow. It is not a field for a Classic patient key. A Classic PK belongs only in the protected crosswalk/provenance layer; for a direct legacy OPD alias this FK should normally be null.

The only implemented normalizer is `PatientAlias::normalize()`: trim outer whitespace, remove all remaining whitespace, then PHP `strtoupper()`. It preserves leading zeros and punctuation, but does not perform explicit Unicode NFC normalization and does not provide a documented Unicode casefold. Because the unique column is only 120 characters, a normalized value longer than 120 is not safely representable even though the display value permits 191.

Confirmed gap: there is no `legacy_opd` alias constant, no alias creation/domain service outside `PatientMergeService`, no legacy-alias validation request, no protected collision-review/release workflow, and no normalization-version field. The current target has zero aliases, but that mutable fact cannot replace a commit-time collision check.

Required Phase 3 prerequisite:

- approve a stable alias type such as `legacy_opd`;
- define versioned raw/display/comparison canonicalization, explicitly including Unicode NFC, whitespace, case, punctuation, and preservation of leading zeros;
- define invalid/blank/overlength behavior;
- preflight duplicates across the entire source and target normalized keyspace;
- query alias owners including soft-deleted target patients;
- withhold every duplicated or target-conflicting OPD alias without decorating it or selecting a “best” owner;
- persist a unique valid alias only after its patient mapping exists;
- use null `created_by` unless separately verified field-semantic actor evidence exists;
- preserve raw Classic OPD only in protected provenance and the approved alias display field, never in generated documentation/log output;
- reconcile patient entity and alias outcomes separately.

The general patient search performs partial `LIKE` matching over alias display and normalized values. It is an operational lookup, not deterministic identity evidence and must never be used to link a Classic patient to an existing target.

## 5. Existing target collisions and soft deletion

Confirmed behavior:

- Eloquent `Patient` uses `SoftDeletes`; default model queries hide soft-deleted patients.
- Database unique keys on `patient_number` and `ghana_card_number` continue to reserve values held by soft-deleted patients.
- `StorePatientRequest`/`UpdatePatientRequest` uniqueness for Ghana Card does not exclude soft-deleted rows.
- aliases are not soft-deleted; a soft-deleted patient continues to reserve its `(type, normalized value)` alias. Force delete cascades aliases and many clinical/financial children.
- patient relationships to registrar, merge actors, and similar users do not use `withTrashed()`.

Required collision rules:

- all target collision preflights must use unscoped/`withTrashed()` patient queries;
- no automatic target match may be made from name, normalized name, OPD/alias, phone, email, DOB, gender, address, Ghana Card alone, similarity, or weighted score;
- the only permitted existing-target link is an explicit protected pre-approved crosswalk or a separately reviewed deterministic identity decision;
- a successful explicit link verifies target existence/state and records conflicts, but never overwrites target identity, timestamps, status, registrar, aliases, or children automatically;
- a link to a soft-deleted or merged target is blocking pending controlled review; it must not be silently restored or redirected;
- target patient-number, Ghana Card, and alias conflicts are separate deterministic exception classes, not merge evidence.

Phone and email are not unique at database level. Ghana Card is unique but unnormalized beyond database collation and has no format validator. Each may be supporting review evidence, never a single-field target match.

## 6. Merge workflow: operational only, never automatic migration

`PatientMergeService` and its request/log tables are not an importer deduplication API.

Confirmed workflow behavior:

- UI requires two patient numbers, a reason, confirmation, and permissions; a user with execute permission can request, approve, and execute immediately.
- Service validation only prevents self-merge, a duplicate already merged, and an already-merged main folder. It does not enforce independent four-eyes approval.
- `estimateMatchConfidence()` scores exact equality of first name, last name, DOB, gender, phone, and Ghana Card. This is advisory code, not authoritative identity matching.
- execution locks rows, creates aliases for the duplicate number/Ghana Card/phone, optionally overwrites selected main demographics, moves/deduplicates insurance, bulk-reassigns a hard-coded child-table list, marks the duplicate inactive/merged, and writes current-time merge/activity logs.
- `PatientMergeGuard` is used by visit and emergency-case creation, but not proven to cover every one of the installed patient-dependent services.
- merge logs and activity metadata can contain patient numbers, alias values, demographics, and other PHI.

The hard-coded merge list is materially smaller than the installed patient dependency surface and includes application-only patient columns. It does not prove that every installed patient FK/relationship is safely reassigned. Therefore direct setting of merge fields is also unsafe.

Migration contract:

- automatic merges, merge requests, and merge executions created by migration = 0;
- suspected duplicates remain separate eligible patient candidates when required identity is valid and receive only a protected migration review flag;
- names, phone, OPD, DOB, gender, Ghana Card, and the built-in confidence score cannot trigger linking or merging;
- any later human-approved merge must use a separately reviewed operational identity process and the domain service, after its full dependency coverage, privacy logging, actor controls, and approval segregation are validated;
- `PatientMergeService` must never be called in a migration commit window.

## 7. Contacts and insurance structures

These child domains are deferred, but they constrain patient persistence order.

### 7.1 Emergency contacts

Installed `emergency_contacts` requires patient, name, and phone; secondary phone/relationship are nullable; `is_primary` defaults false. There is no uniqueness constraint, soft delete, observer, or DB rule limiting one primary contact. Web registration makes the first submitted contact primary.

Validated direct child insertion through a future migration boundary is structurally possible after patient mapping, with events isolated and approved contact validation. It must not populate the dormant inline patient emergency-contact columns. One-primary semantics, normalization, privacy, and source row history remain Phase 2D decisions.

### 7.2 Patient insurance

Installed `patient_insurances` requires patient/provider, has optional tier, card-holder membership, membership/policy/CCC identifiers, dates, and boolean primary/active flags. Native `member_type` is `holder|beneficiary`. Unique `patient_insurance_unique` permits only one row per `(patient_id, insurance_provider_id)`, including inactive/history rows. Provider delete cascades memberships; tier/card-holder delete sets null. There is no soft delete.

Service/application-only invariants include:

- tier must belong to provider;
- only one primary membership should exist per patient;
- beneficiary requires a card-holder membership and is subject to tier maximum beneficiaries;
- card holder/provider/member-type consistency and cycle prevention are not fully database-enforced;
- expired/inactive memberships affect coverage eligibility;
- current/reference provider and tier links must use Phase 2A crosswalks.

The registration controller creates insurance children after the patient and outside an encompassing transaction. It can replace a submitted mismatched tier with the provider’s current default instead of failing, which is unacceptable historical transformation. The separate insurance controller rejects a mismatched tier but is an HTTP workflow, not a reusable membership creation service. `InsuranceService` manages coverage/usages, not membership creation, and must not be called to fabricate historical usage.

Future migration persistence may insert a validated deterministic current membership directly only through the migration boundary after provider/tier/patient maps exist and D-212 consolidation succeeds. It must reproduce the logical invariants, never select a present-day default tier as a substitute for missing evidence, and keep all source rows in protected history/provenance. Conflicting membership candidates remain quarantined. Contacts and insurance must not be allowed to force an unsafe patient identity match.

## 8. Archive and privacy structures

### 8.1 Archive

`ArchiveInactivePatientsCommand` is a current operational action. It chooses active/inactive, nondeceased, nonmerged patients based on current patient/visit/appointment activity; writes `archived_at=now()`; stores full patient attributes plus activity dates in `archived_patients.payload`; then sets current patient status to archived/inactive. `archived_patients.patient_id` is nullable-unique and set null on force delete; copied patient number/full name are indexed and remain after parent removal.

It must not run during migration and historical status must not be interpreted as a request to call it. Archive rows duplicate PHI and require a separate retention/history specification. Direct archive creation, current-time archival, and automatic setting of target `deleted_at` or archived status are outside Phase 2C authorization.

### 8.2 Privacy

Privacy is display/permission masking, not encryption at rest:

- phone/email/address/Ghana Card/insurance identifiers/emergency-contact phone are level 2; allergies/chronic conditions are level 3;
- `patient_number`, gender, age, and DOB are treated as unrestricted level 0 (DOB uses a `date` mask strategy that currently returns the original value);
- first/last/other names are absent from the field registry, so generic privacy display returns them unchanged;
- `Patient::scopeSearch()` queries raw first/last/other name, patient number, phone, email, Ghana Card, insurance membership, emergency contacts, and aliases;
- profile viewing and break-glass can create activity records;
- privacy directives require non-null patient and creator; overrides require a user, reason, and current time window.

`Patient` uses Spatie `LogsActivity` and logs dirty `first_name`, `last_name`, and `status`. This bypasses `ActivityLogService::SENSITIVE_FIELDS`; names are not in that sanitizer in any case. Ordinary Eloquent patient creation/update can therefore create contemporaneous activity containing raw names. `Model::withoutEvents()` or a query-builder boundary is required for historical rows, and migration audit must remain separate and non-PHI.

Privacy directives and break-glass overrides are operational authorization records. They may not be directly imported or synthesized from general patient data; a source-evidenced directive would require its own actor, chronology, legal-retention, and field contract. No historical view/break-glass activity should be fabricated.

Avatar handling is a separate filesystem/PHI side effect. Migration must neither call normal avatar store/delete nor copy files until an approved protected file migration contract exists.

## 9. Direct persistence versus existing services

“Direct” below means only the controlled transactional migration persistence boundary defined in `TARGET_CREATION_RULES.md`, with target validation, mappings, events/integrations isolated, timestamps explicit, and reconciliation. It never means raw unvalidated copy.

| Target record/action | Contract |
|---|---|
| New patient core | Direct validated persistence is required after safe target-number allocation. Do **not** call `PatientService::create()` unchanged because it stamps Auth, current timestamps, may write files, and lacks crosswalk/child transactionality. |
| Patient number sequence | Must reuse/reproduce the configured format and row-lock invariant in a migration-specific allocator. Do not update ad hoc, use the old model helper, or accept the current service’s collision suffix/idempotency defects. |
| Unique valid `legacy_opd` alias | Direct validated insert is permissible after patient mapping and all source/target duplicate checks, once alias type/normalization/privacy prerequisites are approved. Do not use `PatientMergeService`. |
| Emergency contact | Direct validated insert is structurally permissible after patient, deferred to Phase 2D; enforce privacy and one-primary policy explicitly. |
| Deterministic current patient insurance | Direct validated insert is permissible only after patient/provider/tier maps and D-212 consolidation; reproduce membership invariants. No existing membership domain service provides a safe historical API. |
| Existing target patient explicit link | Crosswalk-only; no target patient update. |
| Suspected duplicate | Protected review flag only. No target merge row/action automatically. |
| Approved post-migration merge | Existing reviewed merge domain workflow/service, never direct field/child updates and never migration automation; service coverage gaps must first be closed. |
| Archive | Operational archive workflow only after migration/cutover when genuinely requested; do not infer or direct-create during identity import. |
| Privacy directive/override | Operational authorized workflow only; do not direct-create from migration without a separate source-evidenced legal/actor contract. |

No existing patient-domain service is safe unchanged as the historical patient importer entry point.

## 12. Required dependency order

1. Freeze/fingerprint the installed target schema, patient runtime configuration, target collision baseline, and integration/isolation state.
2. Create/approve Phase 3 migration foundation contracts: protected crosswalk, provenance, quarantine/chain ledger, exception ledger, checkpoints, reconciliation, migration audit, and target-specific number allocator. No such persistence is authorized in Phase 2C.
3. Resolve prerequisites that can block a patient: required-field validity, explicit existing-target crosswalks, target patient-number/Ghana Card conflicts, and source remediation decisions.
4. Persist/map the patient core and generated patient number atomically. `registered_by` is null under the current Phase 2B contract.
5. After the patient crosswalk exists, insert a unique valid typed legacy OPD alias; withhold duplicate/invalid/conflicting aliases without blocking an otherwise valid patient.
6. Phase 2D may add contacts/demographic children after patient mapping. Phase 2E may add insurance only after Phase 2A provider/tier mappings and membership consolidation/card-holder order are resolved.
7. Visits/appointments and all clinical, admission, finance, claim, pharmacy, maternity, emergency, privacy, archive, and operational children follow their own later-phase mappings. Quarantined patient chains cannot be partially released.
8. Post-migration suspected-duplicate review may occur only after complete child graphs and protected review controls exist; no automatic merge is part of this order.

## 13. Confirmed service-only invariants

- configured patient number format plus unique `(prefix, period type, period key)` locked sequence;
- idempotent source mapping must precede allocation (required by migration policy, absent from current service);
- patient enum compatibility for gender/blood group/marital status;
- operational request limits/format rules stronger than DB widths;
- coherence among status, active, temporary, merge, death, confirmation, and actor fields;
- merged folders cannot receive new visits/emergency cases, although guard coverage is not universal;
- one primary contact and one primary insurance are controller conventions, not DB uniqueness;
- provider-tier, beneficiary/card-holder, maximum-beneficiary, validity, and current-membership rules;
- target search results and merge confidence are not identity evidence;
- timestamps and actor attribution must be source-evidenced, not runtime-generated.

## 14. Historical-accuracy and privacy risks

Confirmed high-risk paths:

- normal creation overwrites number/registrar and stamps current time;
- sequence allocation can commit without a patient and collision suffix is nondeterministic;
- web parent/child creation is non-atomic;
- registration can silently replace a mismatched insurance tier with a current default;
- direct DB insertion can accept invalid enum/status combinations, future/implausible DOB, malformed phone/email/Ghana Card, and incoherent merge/death states;
- temporary emergency and newborn services intentionally invent names, dates, gender/phone placeholders for operational workflows; these are expressly prohibited migration precedents;
- merge execution creates present-time evidence, PHI-rich logs, broad updates, and may not cover all installed relationships;
- archive duplicates full patient PHI and current-time state;
- patient names can enter Spatie activity logs and are not covered by current privacy-field masking;
- default Eloquent scopes hide soft-deleted collision owners;
- alias normalization is not Unicode-NFC/versioned and its unique comparison capacity is shorter than display capacity;
- target unique collation semantics can collapse values that source comparison rules consider distinct;
- direct/force deletion can cascade a large historical graph; delete-and-recreate is never an idempotency strategy.

Blocking prerequisites before Phase 3 patient persistence:

2. protected source-target crosswalk and source row fingerprint, with no raw identifiers in logs/docs;

4. versioned target runtime configuration fingerprint;
5. approved `legacy_opd` type, Unicode/canonicalization/version contract, collision review and release mechanism;
6. patient quarantine/dependent-chain ledger and exact reconciliation partitions;

8. approved operational-vs-physical required-field limits and stable field-specific exceptions;
9. explicit patient status/temporary/merge/death state matrix;
10. migration isolation gates for events, audit, queue, schedulers, files, notifications, and downstream domain services;
11. privacy/provenance controls for names, aliases, crosswalks, activity, archive payloads, and diagnostics using domain-separated versioned HMAC where row-level correlation is unavoidable;
12. target-side child relationship validation for the eight non-FK patient columns;
13. post-migration merge workflow review covering all installed dependencies and segregation of approval;
14. Phase 2A provider/tier readiness and Phase 2B actor contract consumption.

Unresolved questions requiring consolidation, not assumptions:

- whether the logical migration maximum for patient name components is the operational request maximum 100 or a separately approved migration representation up to the physical 191;
- exact DOB lower bound/partial-date representation (DB supplies no answer; no unknown representation is approved);
- exact legacy OPD validity grammar and Unicode canonicalization;
- approved target status for a valid historical patient whose Classic active/archive semantics do not map exactly;
- whether any source-evidenced patient archive/privacy fact is in scope later and what retention/actor rules would apply;
- whether the current runtime numbering pattern is a cutover-frozen institutional contract or merely environment configuration requiring owner approval.
